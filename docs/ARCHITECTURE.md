# MLB Game — 아키텍처 & 최적화 원칙

야구판 Football Manager 스타일 웹게임. **저사양 서버에서의 최적화**가 핵심 과제.

## 1. 스택

| 항목 | 선택 | 비고 |
|---|---|---|
| 언어 | Java 21 | 가상 스레드, record, sealed, pattern matching 활용 |
| 프레임워크 | Spring Boot 4.1.2 | |
| 빌드 | Gradle 9.8.2 (wrapper) | |
| DB | MySQL 8.0.46 | 스키마는 Flyway 로 관리 |
| 영속성 | JPA(일반 CRUD) + JdbcTemplate(대량 쓰기·집계) | 아래 3-2 참고 |
| 캐시 | Caffeine (로컬) | Redis 는 서버 1대 기준이라 도입 안 함 |

## 2. 배포 구조 (경로)

운영 점검(요청·작업 시간 로그, 지표, 동시 부하 벤치마크, 서버 설정): [OPERATIONS.md](OPERATIONS.md)

같은 도메인에서 `/game` 은 이미 다른 서비스가 사용 중. 이 서비스는 `/` 에 배포.

```
            ┌─ /game, /game/*  →  기존 서비스
nginx ──────┤
            └─ / (나머지 전부)  →  mlb-game :8080
```

규칙:
- 이 앱은 **context-path 없이 `/`** 에서 동작. `/game` 으로 시작하는 경로는 **절대 만들지 않는다.**
- 세션 쿠키 이름을 `MLBSID` 로 변경. (`path=/` 쿠키는 `/game` 요청에도 전송되므로, 기존 서비스가 `JSESSIONID` 를 쓰면 충돌 가능)
- 기존 서비스 쿠키(`path=/game`)는 우리 앱에 오지 않으므로 신경 쓸 필요 없음.
- 관리 엔드포인트(actuator)는 `127.0.0.1:8081` 에만 열림 → 외부 노출 없음.

nginx 예시 (`location` 은 더 긴 prefix 가 우선이라 순서 무관하지만, 명시적으로 `^~` 사용):

```nginx
location ^~ /game {
    proxy_pass http://127.0.0.1:<기존서비스포트>;
    # ... 기존 설정 유지
}

location / {
    proxy_pass         http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header   Connection "";
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
}

# 정적 리소스(/css, /webjars)는 앱이 서빙. 트래픽이 늘면 nginx 직접 서빙 + 장기 캐시로 전환
# location ^~ /static/ { alias /srv/mlb-game/static/; expires 30d; access_log off; }

gzip on;
gzip_types text/css application/javascript application/json image/svg+xml;
gzip_min_length 1024;
```

## 3. 최적화 원칙

### 3-1. 시뮬레이션은 메모리에서, DB 는 결과만
- 경기 시뮬레이션(타석/투구 단위)은 **순수 Java 객체로 메모리에서 계산**. 시뮬 중 DB 접근 금지.
- 저장은 **경기 요약 + 박스스코어 + 누적 스탯 증분**만. 투구 단위 로그는 저장하지 않거나, 필요 시 압축 blob 으로 1행 저장.
- 시뮬 엔진은 Spring 의존성 없는 패키지로 분리 → 단위 테스트·벤치마크 용이.
- 난수는 경기별 seed 기반 `SplittableRandom` → 재현 가능 + `Random` 보다 빠름.

### 3-2. 쓰기 최적화
- MySQL 에서 `IDENTITY` 전략 엔티티는 **Hibernate 배치 INSERT 가 비활성화**됨.
  → 대량 쓰기(경기 결과, 시즌 스탯, 선수 생성)는 `JdbcTemplate.batchUpdate` + `rewriteBatchedStatements=true` 로 처리.
- 스탯 누적은 "행 단위 UPDATE N번" 대신 `INSERT ... ON DUPLICATE KEY UPDATE` 배치 1번.
- 하루치(또는 한 라운드) 경기를 묶어 **한 트랜잭션 / 한 배치**로 저장.

### 3-3. 읽기 최적화
- `open-in-view: false` — 커넥션은 서비스 계층 안에서만.
- 화면용 조회는 엔티티 대신 **DTO projection** (필요한 컬럼만).
- 리그 구조, 팀 기본정보, 능력치 테이블 같은 **거의 안 바뀌는 데이터는 Caffeine 캐시**.
- 순위표·리더보드는 매 요청 집계하지 않고 **시뮬 후 갱신된 집계 테이블**을 읽음.
- 인덱스는 실제 쿼리 기준으로 설계, 슬로우 쿼리는 `EXPLAIN` 으로 검증.

### 3-4. 동시성 / 리소스
- 가상 스레드 사용. 단, DB 동시성의 실질 상한은 Hikari 풀(기본 8, 운영 6).
- 시뮬레이션 같은 CPU 작업은 가상 스레드가 아니라 **코어 수 기준 고정 풀**에서 실행.
- 장시간 작업(시즌 일괄 진행 등)은 요청 스레드에서 돌리지 않고 비동기 잡 + 진행상태 폴링.

### 3-5. JVM (운영 서버 스펙 확정 후 조정)
```
-Xms<N>m -Xmx<N>m              # 동일 값으로 고정 (힙 리사이즈 비용 제거)
-XX:+UseSerialGC               # 1~2 vCPU / 힙 1GB 이하일 때. 그 이상이면 G1 기본값
-XX:MaxMetaspaceSize=192m
-Xss512k
-XX:+ExitOnOutOfMemoryError
-Duser.timezone=Asia/Seoul
```
- 추가 후보: CDS(Class Data Sharing) 아카이브로 기동 시간·메모리 절감.

### 3-6. MySQL
- 서버에 바이너리로 직접 설치한 MySQL 8.0.46 기준 (Docker 미사용).
- [`config/mysql/mlbgame.cnf`](../config/mysql/mlbgame.cnf) 내용을 서버의 `my.cnf`(`[mysqld]` 섹션)에 반영.
  저사양 기준으로 `performance_schema=OFF`, 버퍼풀 축소.
- 운영 서버 메모리가 정해지면 `innodb_buffer_pool_size` 재조정.

## 5. 게임 범위 (2026-11-02 결정)

| 항목 | 결정 | 설계 영향 |
|---|---|---|
| 플레이 방식 | 순수 싱글 커리어 | 유저 간 상호작용 없음. 커리어 단위로 데이터가 완전히 분리됨 |
| 시간 진행 | 유저가 "다음 날" 버튼으로 진행 | 서버 스케줄러 불필요. 요청 1번 = 하루치 경기(최대 15경기) 처리 |
| 리그 규모 | MLB 와 동일 (30팀, 162경기) | 시즌당 2,430경기 |
| 선수 데이터 | 실제 데이터 기반 | 외부 데이터 → 능력치 변환 배치 필요. 런타임에 외부 API 호출 금지 |
| 경기 관전 | 결과만 (박스스코어) | 타석/투구 로그 저장 안 함. 시뮬은 타석 단위로 충분 |
| 마이너/뎁스 | 보류 | 메이저 26인/40인 기준으로 먼저 만들고, 기능 테스트 후 규모 산정 |
| 커리어 기간 | 다년 커리어 (성장·노화·은퇴·드래프트·포스팅, 계약·FA 단순화) | 오프시즌 처리 필요. 상세: [CAREER.md](CAREER.md) |
| 사용자 | 로그인 기반, 유저별로 독립된 커리어 보유 | 인증 필요. 커리어 수 = DB 크기 상한 요인 |
| 데이터 소스 | 최대한 하이퍼리얼 (개인·비상업) | MLB Stats API + Baseball Savant(Statcast) |
| 시점 | 2026 시즌 개막에서 시작. 과거 기록은 2025 까지 | 능력치는 2026 시즌 종료 시점 실적으로 산정 |

### 데이터 구조 원칙 (위 결정에서 도출)
- **마스터 데이터**(실제 선수·팀 원본, 읽기 전용, 모든 커리어 공유)와
  **커리어 데이터**(커리어별로 변하는 선수 상태·로스터·기록)를 분리.
- 커리어 데이터 테이블은 모두 `career_id` 를 PK/인덱스 선두 컬럼으로 둠.

### 커리어별 능력치 분포 (커리어 생성 시 1회)
마스터 능력치를 그대로 복사하지 않고, **마스터 값을 중앙값으로 하는 절단 정규분포**에서 뽑는다.
같은 선수라도 커리어마다 조금씩 다르다.

```
값 = TruncNormal(평균 = 마스터값, 표준편차 = σ_기본 × 가중치, 범위 = 마스터값 ± k·σ)
     → 최종적으로 전체 스케일(20~80) 안으로 제한
```
- 절단은 범위 밖 값이 나오면 **다시 뽑는 방식**(clamp 로 자르면 경계값에 몰림).
- 가중치(σ 배율) 후보:
  - 표본 신뢰도: 2026 타석/이닝이 적을수록 σ 증가 (데이터가 불확실한 선수일수록 변동 큼)
  - 나이: 젊을수록 σ 증가, 베테랑은 감소
  - 능력치 종류: 측정이 정확한 항목(구속, 스프린트 속도)은 작게, 추정 성격 항목(수비, 멘탈)은 크게
- 커리어별 seed 저장 → 같은 커리어는 재현 가능.
- 구현: 마스터 선수 데이터를 메모리 캐시에서 읽어 Java 로 샘플링 → 커리어 테이블에 배치 INSERT.

### 실제 데이터 파이프라인
- 게임 서버와 분리된 **임포터**(개발 PC 에서 실행) → 마스터 테이블 적재. 게임 실행 중 외부 호출 없음.
- MLB Stats API: 팀, 2026 개막 로스터(40인), 선수 프로필(나이·투타·포지션), 2025 까지 시즌 기록, 2026 실제 일정.
- Baseball Savant: 타구 속도·발사각, 배럴, 헛스윙/추격 비율, 구속·회전수·구종, 스프린트 속도, OAA(수비), 송구, 포수 프레이밍·팝타임.
- 2026 실적 → 능력치 변환 (마스터 값). 표본이 작은 선수는 2024~2025 실적과 리그 평균으로 보정.
- 외부 요청은 속도 제한을 두고, 받은 원본은 로컬에 캐시해서 재요청 최소화.

### 확정 기본값
- 유저당 커리어 슬롯: **3개**
- 분포: 20~80 스케일, **σ = 3, 범위 ±2σ** (가중치 반영 시 유망주 약 ±8, 베테랑 약 ±4)
- 2026 실적 중심, 표본이 적은 선수만 2024~2025 실적 + 리그 평균으로 보정

## 6. 능력치

모두 20~80 스케일. 좌우 상대 분리 없이 **통합 평균값 1개**로 산정.
(투타 상성은 선수별 저장 없이 리그 평균 플래툰 보정 상수로만 반영 — 저장 비용 0)

| 구분 | 항목 |
|---|---|
| 타자 | 컨택, 파워, 선구안, 타구 질, 타구 성향(성향값), 스피드, 주루 |
| 투수 | 구종별 구위·구사율(하위 테이블), 제구, 피안타 억제, 스태미나 |
| 수비 | 포지션별 수비 범위, 송구, 포수(프레이밍·팝타임·블로킹) |
| 숨김 | 내구성, 잠재력, 성격(아래 발휘 시스템) |

저장: 항목별 `TINYINT UNSIGNED` 컬럼, 선수 1명 = 1행 (EAV 금지). 구종만 하위 테이블.

### 발휘 시스템 (능력치를 얼마나 끌어내는가)
실제 능력치는 그대로 두고, 경기에서 **발휘되는 비율**을 상태값으로 조절.

- 고정 성격(숨김, 커리어 생성 시 분포 샘플링): 적응력, 멘탈 안정성, 프로의식
- 변동 상태:
  - 사기: 출전 기회, 팀 성적, 연봉 만족 등
  - 팀 적응도: 이적 직후 낮고 시간이 지나며 상승 (적응력이 속도 결정)
  - 감독 신뢰도: 기대한 역할·출전 시간과 실제의 차이로 변동
  - 역할 적합도: 선발↔불펜 전환, 비주전 포지션 기용 시 하락
- 발휘율 = f(상태값들), **상·하한 고정** (예: 90%~105%) → 극단적 결과 방지

최적화:
- 발휘율은 타석 시점에 **로그 오즈 보정 1회**로 적용 → 선수별 확률표 캐시를 다시 계산하지 않음.
- 상태값은 매일 전원 UPDATE 하지 않음. `값 + 마지막 갱신일` 만 저장하고 시간 경과(회복·감쇠)는 **읽을 때 계산**.
  실제 UPDATE 는 이벤트(트레이드, 기용 변화, 연승·연패 등)가 있는 선수만.

### 스카우트 추정치
유저에게 보이는 능력치는 **범위**(예: 45~55)이며, 팀 스카우트 수준이 높을수록 범위가 좁아짐.

```
폭 w        = f(스카우트 수준, 자기 팀 선수 여부, ...)
선수별 오프셋 u ∈ [-1, 1]   (career seed + 선수 + 항목으로 결정적으로 생성, 저장 안 함)
표시 중심   = 실제값 + u × w × 0.5
표시 범위   = [중심 - w, 중심 + w]   → 항상 실제값을 포함
```
- 같은 u 를 계속 쓰므로 새로고침해도 값이 바뀌지 않음 (여러 번 보고 평균 내는 꼼수 차단).
- 스카우트 수준이 오르면 범위가 실제값 쪽으로 **일관되게 좁아짐**.
- 추정치는 저장하지 않고 조회 시 계산 → 저장 비용 0.
- 숨김 능력치(잠재력, 성격)도 같은 방식으로 "추정" 형태로만 노출.

### 확정 기본값 (튜닝 가능)
- 발휘율 범위: **0.90 ~ 1.05** (`sim.Performance`)
- 스카우트 수준 5단계, 표시 폭 w: 1단계 ±12 / 2단계 ±9 / 3단계 ±6 / 4단계 ±4 / 5단계 ±2.
- 단계 변경 (`offseason.Scouting`, 대시보드 오프시즌 카드): 오프시즌 1~4단계(FA 시장 개장 전)에만, 개장 뒤 다음 오프시즌까지 고정.
  연 비용 (1단계 대비) 1 $0 · 2 $2M · 3 $5M · 4 $9M · 5 $15M, 내 팀 재계약·FA 제안의 예산 확인에서 뺀다
  (구단 예산 값 자체는 그대로: 리그 시장 규모 = 예산 합이라 깎아 저장하면 비율이 해마다 줄어듦).
  자기 팀 선수는 한 단계 위로 취급.

## 9. 화면 (구현: `web` 패키지)

- 서버 렌더링(Thymeleaf) + htmx. 별도 프론트 빌드 없음, htmx 는 WebJar(`/webjars/htmx.org/2.0.4/...`)로 jar 에 포함.
- 로그인: Spring Security 폼 로그인, BCrypt(강도 10), 세션 쿠키 MLBSID, CSRF 켜짐 (모든 POST 는 th:action 폼 → 토큰 자동 포함,
  htmx 요청도 폼 필드를 그대로 보냄). CLI 프로필(web-application-type=none)에서는 필터 체인을 만들지 않음.
- 커리어 경로는 모두 소유자 확인 (남의 커리어 ID 는 404). 삭제는 deleted_at 표시 (데이터 정리는 추후 일괄).
- 화면: 가입·로그인 / 커리어 슬롯 3개 (생성·이어하기·삭제) / 대시보드 (오늘 경기·내 팀 최근 경기·포스트시즌·순위,
  "다음 날"·"1주"·"정규시즌/포스트시즌 끝까지"(한 요청에서 다음 날 반복, 하루씩 저장, 최대 220일)·오프시즌 "다음 단계" 버튼은 htmx 로 본문만 교체, 오프시즌 중에는 단계 진행 현황·결과 요약·드래프트 1라운드 추첨 결과·내 지명권 표시) / 순위 / 팀 로스터 (MLB·AAA·AA) / 선수 / 박스스코어.
- 능력치는 스카우트 범위로만 표시 (`ScoutView`, 6번 규칙). 숨김 능력치(잠재력·내구성)는 1.5배 넓은 범위.
- 조회는 화면당 쿼리 1~3개 (`CareerQueries`), 선수 신상은 mst_player 또는 c_person 중 있는 쪽 (LEFT JOIN 2개).
- 운영 지정 (`/careers/{id}/tactics`, 내 팀 MLB 만): 우투수/좌투수 상대 타순(선수+수비 위치), 5인 로테이션 순서,
  불펜 우선순위([0]=마무리), 주전 휴식 자동 교체 on/off. 항목별로 "지정"을 끄면 AI 자동.
  - 저장: c_tactic 1행 (V11, 문자열 "선수ID:위치,..."). 저장 즉시 메모리 팀 구성을 다시 만들어 다음 경기부터 반영
    (`TacticService`, "다음 날"과 같은 커리어 잠금).
  - 적용: `AutoManager.build(team, roster, TeamPlan)` 이 지정 자리를 먼저 채우고, 오늘 뛸 수 없는 지정 선수(부상·강등)의
    자리만 자동 규칙으로 메운다 → 복귀하면 다시 지정대로. 로테이션은 5명까지 스태미나 순, 불펜은 지정 뒤에 구위 순으로 붙음.
  - 타순을 지정하면 자동 플래툰 교체 없음 (좌투수 상대 타순으로 직접 정함). 휴식 교체 판정 난수는 설정과 무관하게 같은 횟수 사용.
  - AI 의 자동 강등(부상 복귀·월요일 교체)은 지정 선수를 가장 뒤로 미룬다.
- 로스터 이동 (내 팀 로스터 화면의 "이동" 열, `MoveService` / 규칙 `RosterMoves`): 콜업, MLB → AAA/AA 강등(40인 유지),
  AAA ↔ AA, 40인 등록/제외. 즉시 c_player 1행 저장 + 해당 레벨 팀 구성 재생성. 오프시즌에는 막음.
  - MLB 현역 최대 26명, 40인 최대 40명 (현역 + MLB 부상자 + 산하 팀 40인), 마이너 계약 선수 콜업 = 40인 등록 포함.
  - 부상 선수 콜업 불가, MLB 부상자 명단은 강등 불가, MLB 유형별 현역 10명 미만으로는 못 내림,
    AAA ↔ AA 는 떠나는 팀 최소 인원(DayRules.MIN_AAA/MIN_AA) 유지.
  - 40인 40명은 전 구단 공통으로 유지: AI 자동 콜업(부상 대체·빈 자리 채움)으로 넘치면 산하 팀 40인 중 가치 최하위부터
    40인 제외 (`DayRules.trimFortyMan`, 매일 경기 전후). 커리어 적재 시에도 한 번 정리해 바로 저장
    (생성 직후 실제 로스터 자료·오프시즌 재배치·규칙 도입 전 커리어의 초과분).
  - 26명보다 적게 두면 다음 경기 전 AI 가 채움. 부상 대체 콜업·복귀 강등은 항상 자동, 월요일 자동 교체는 끌 수 있음 (c_tactic.auto_swap, V12).
- 드래프트 화면 (`DraftController`): 지명 순서(지금 차례 앞뒤 10장)·내 지명권·후보 상위 100명(전체/타자/투수, 스카우트 범위).
  "1주"·"시즌 끝까지"·"남은 단계 한 번에"는 테스트 기능 (`web.DevTools`): local 프로필에서만 보이고, 운영(prod)은 화면에서 숨기고 요청도 404.
  `app.dev-tools: true/false` 로 강제 가능.
- 득점 환경 점검: 시즌 벤치마크 (`SeasonBenchRunner`) 마지막에 시즌별 리그 평균 추이 표
  (득점/G·타율·출루·장타·홈런%·삼진%·볼넷%·BABIP, MLB 26인 평균 능력치, 실제 2026 행).
  `--spring.profiles.active=local,season-bench --spring.main.web-application-type=none --bench.seasons=6 --bench.quiet=true`
- 계약 결정 화면 (`ContractController`): FA 자격 선수 재계약(연수 선택)/포기, 연봉조정 선수 텐더/논텐더,
  결정 후 연봉 합계·예산 실시간 표시. "저장" 또는 "저장하고 다음 단계"(5단계 진행).
- FA 시장 화면 (`FaController`): 6라운드 입찰. 예산·제안 합계, 내 제안과 반응, 시장 선수 상위 150명(스카우트 추정 가치 순, 전체/타자/투수),
  선수별 요구액·관심 구단 수·제안 입력(연봉 $M·연수), 이번 시장 계약 목록. 라운드 진행 → 6라운드 뒤 "FA 시장 마감".
- 트레이드 화면 (`TradeController`, `season.TradeService`·`TradeRules`, 표 `c_trade`): 상대 구단을 고르고 양쪽 로스터(MLB·AAA·AA)에서
  선수를 체크(한쪽 최대 5명) → 제안 → AI 가 바로 수락/거절 ("가치가 조금/많이 부족", 40인·예산 초과 안내). 오가는 연봉과 트레이드 뒤
  40인·연봉 합계는 화면에서 미리 계산. 기간: 정규시즌 개막 ~ 7월 31일, 오프시즌 FA 시장 마감 뒤 ~ 개막 전.
  시즌 중에는 메모리 상태에서 소속 이동 → 26인 초과 강등·부족 콜업 → 바뀐 선수 행만 저장 + 팀 구성 재생성, 오프시즌은 소속만 저장.
  AI 평가 = 남은 보유 기간 잉여 가치 Σ 0.9^t (기대 시장가치 - 연봉), 나이별 성장·노화 예상, 유망주 실패 위험 ×0.6,
  윈나우(승률 .530+) 올해 ×1.5 / 리빌딩(.470 미만) 올해 ×0.6·연봉 부담 ×1.2·25세 이하 ×1.15, 포지션 부족 ×1.1.
  수락 = 받는 가치 ≥ 주는 가치 + max(30만, 7%). 지명권·AI 끼리 트레이드·역제안은 아직 없음 (2차).

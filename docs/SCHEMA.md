# DB 스키마 & 저장 전략

마이그레이션: `src/main/resources/db/migration/V2__core_schema.sql`

## 1. 규모 추정이 설계를 결정한다

커리어 1개, 시즌 1개 기준:

| 데이터 | 단순 설계 (행 단위) | 이 설계 |
|---|---|---|
| 경기 결과 | 2,430 행 | 2,430 행 |
| 타자 박스스코어 | 43,740 행 (18 × 2,430) | **0 행** (경기 행에 바이너리로 포함) |
| 투수 박스스코어 | 약 21,000 행 | **0 행** (경기 행에 바이너리로 포함) |
| 시즌 누적 스탯 | 경기마다 갱신 | 선수당 1행, 하루 1번 배치 upsert |

커리어 300개(유저 100명 × 슬롯 3)라면 단순 설계는 **시즌당 약 2,000만 행**, 이 설계는 **약 73만 행**.

## 2. 테이블 구분

| 접두사 | 성격 | 예 |
|---|---|---|
| `mst_` | 마스터. 실제 데이터, 읽기 전용, 모든 커리어 공유 | 팀, 선수, 능력치 원본, **2026 실제 일정**, 2025 까지 과거 기록 |
| `app_` | 계정 | 유저 |
| `career` | 커리어 메타 (진행 날짜, seed, 스카우트 수준) | |
| `c_` | 커리어 데이터. PK 선두 = `career_id` | 커리어별 선수, 팀 순위, 경기, 시즌 스탯 |

### 핵심 결정
1. **일정은 복사하지 않는다.** 2026 실제 일정(2,430경기)은 `mst_schedule` 한 벌을 모든 커리어가 공유.
   `c_game` 에는 치른 경기 결과만 `game_no` 로 연결.
2. **박스스코어는 바이너리 1개**(`c_game.box`, 경기당 약 500바이트).
   경기 상세 화면은 행 1개 읽고 디코딩. 시즌 기록·리더보드는 `c_player_season` 에서 읽음.
3. **좁고 고정된 하위 항목은 컬럼으로 펼친다.**
   포지션별 수비(8개)·구종(8종)을 하위 테이블 대신 `c_player` 컬럼으로 → 선수 1명 = 1행 = 1번 읽기.
   해당 없음은 NULL (InnoDB 는 NULL 비트맵이라 공간 거의 안 씀).
4. **PK 선두가 `career_id`** → 한 커리어의 데이터가 디스크에 연속으로 모임 (clustered index).
   모든 조회가 커리어 범위 스캔이 된다.
5. **커리어 테이블에 FK 없음.** FK 검사·잠금 비용 제거, 무결성은 애플리케이션이 보장.
6. 타입 최소화: 능력치 `TINYINT UNSIGNED`, 팀 `SMALLINT`, 경기 번호 `SMALLINT`, 커리어 `INT UNSIGNED`.

### 마스터 적재 (임포터, `com.mlbgame.importer`)
- `import` 프로필로 실행, 완료 후 종료. 개발 PC 에서 실행해 DB 에 직접 적재.
- 일정: 연기 경기 중복 제거 후 정확히 2,430경기 (실제 취소 1경기도 원래 날짜로 포함 → 팀당 162경기).
- 로스터: 일정의 첫 경기일(2026-03-25) 기준 40인 + 개막 26인.
- `mst_bat_season` / `mst_pit_season` 에는 **2026 도 저장** (능력치 산정용). 화면의 과거 기록은 2025 까지만 노출.

## 3. "다음 날" 처리 흐름

```
1. UPDATE career SET cur_date = cur_date + 1일, version = version + 1
   WHERE id = ? AND version = ?            ← 중복 클릭/동시 요청 차단 (영향 행 0 이면 거절)
2. 그날 일정 조회 (mst_schedule, 캐시)       ← 최대 15경기
3. 출전 팀 SimTeam 구성                     ← 커리어별 캐시 (로스터 변경 시 무효화)
4. 메모리에서 시뮬레이션                     ← DB 접근 없음, 약 1ms
5. 한 트랜잭션에서 배치 저장
   - c_game          INSERT 최대 15행 (박스스코어 바이너리 포함)
   - c_team          UPDATE 30행 이내 (승패·득실)
   - c_player_season INSERT ... ON DUPLICATE KEY UPDATE 약 400행 (하루치를 메모리에서 합산 후 1번)
```
목표: 버튼 응답 **100ms 이내** (대부분 5번 배치 저장 시간).

### 캐시
- `mst_*` 전체: 기동 시 또는 최초 접근 시 메모리 적재 (일정 2,430행, 선수 수천 명 수준).
- 커리어별 SimTeam 묶음: Caffeine, 최대 N개 커리어, 일정 시간 미사용 시 제거.
  유저가 연속으로 "다음 날"을 누르면 2일차부터 로스터 조회 생략.

## 4. 커리어 생성

1. `career` INSERT
2. 마스터 능력치를 메모리 캐시에서 읽어 **절단 정규분포 샘플링** (Java)
3. `c_player` 배치 INSERT (약 1,200행), `c_team` 30행
→ 목표 1초 이내.

## 5. 커리어 삭제

수십만 행 `DELETE` 를 한 번에 하면 잠금·undo 로그 부담이 크다.
→ `career.deleted_at` 표시 후 즉시 응답, 백그라운드에서 테이블별 `DELETE ... LIMIT 5000` 반복.
